# Automap field notes

A running log of building Spintacular with Automap 0.1.0 (CLI `cli-v0.1.0`, map release `map-2026.11.07`), written as the work happened. Spintacular is a proof for Automap, so every step with the CLI, the map and the glue is recorded here, with what worked and what didn't. `report.md` beside this file sorts the findings by theme.

Each entry is marked:

- **OK** worked as documented.
- **FRICTION** worked, but cost time or needed a guess.
- **GAP** something Automap doesn't do, or does inconsistently.
- **ENV** a problem of this build's sandbox, not of Automap; kept because other agent sandboxes will hit it.

The build ran in a Linux cloud container (Ubuntu 24.04, clang 18, CMake 3.28, 4 cores) driven by a coding agent, with Windows builds on GitHub Actions.

## 1. Installing the CLI

1. **FRICTION: the README's install line isn't the release.** The README says `go install github.com/zach/automap/cmd/automap@latest`. The release `cli-v0.1.0` ships static binaries (`automap-0.1.0-linux-amd64`, `-windows-amd64.exe`, `-darwin-arm64`) and a `.sha256` file, which is the better route for a game developer with no Go toolchain, but neither the README nor the router skill mentions them. I downloaded the Linux binary from the release and checked its SHA-256 by hand.
2. **GAP: no `--version`, `version`, `help` or `<command> --help`.** Each prints `unknown command` and the full usage, with exit status 2. The version is only visible as `cli_version` inside a `--json` result. An agent checking what it installed has to run `automap find --json` to learn it.
3. **GAP: the usage text leaves out `upgrade`.** `automap` with no arguments lists nine commands. The README, the spec and the router skill all document `upgrade`, and the usage doesn't.
4. **OK: no setup.** The binary needed nothing else: the first `find` fetched the newest map release and its evidence into `~/.cache/automap/`.

## 2. Looking at the map

5. **OK: `automap find` (human output)** is one readable line: 13 libraries and their versions.
6. **FRICTION: `automap find --json` is about 600 lines for 13 libraries.** Nearly all of it is evidence: one object per binding per platform (three platforms), every one `probed` and `current`. The facts I wanted first, which slots each library fills and what it is, aren't in the entries at all; I had to run `show library` for each. For an agent this is context spent on nothing. A summary per library (`slots`, `license`, worst evidence state per platform) with evidence detail left to `show` would serve the job better.
7. **OK: `automap show library sdl3 --json`** is thorough: slots, license class, contribution policy, pins with content hashes, per-variant vcpkg features, allocation and diagnostics hooks, lifecycle steps, GPU backend per platform and the headless environment. This is the information I'd otherwise dig out of headers and docs.
8. **FRICTION: system dependencies are prose.** `facts.platform.system_dependencies["linux-x64-clang"]` is one English sentence naming apt packages for X11, Wayland, autotools and a Vulkan driver. It was accurate (I installed exactly those and the build went through), but it can't be fed to `apt-get`, and neither `start` nor `verify` checks for them or mentions them. I only found the sentence by walking the JSON paths of `show`.

## 3. `automap start`

9. **OK: `start` wrote a coherent composition in under a second:** manifest, lock, vcpkg files, a CMake project, 30 glue files, the `AGENTS.md` section and the router skill. The `AGENTS.md` section is short and right: where the manifest and lock are, the slots, the build, test and run commands.
10. **OK: `--platform`** let me name Windows and Linux only; the manifest records it.
11. **OK: the failure result is honest and useful.** In a trial directory `start` built, failed, and said so: `ok: false`, `level: none`, `BUILD_FAILED` with the log as `details_file`, exit status 1. The evidence file it wrote marks every rule `unverifiable` with the reason. Nothing claimed more than happened.
12. **FRICTION: the summary of a failed start reads oddly:** "the composition is none on linux-x64-clang: BUILD_FAILED".
13. **ENV: source downloads were blocked.** This sandbox's proxy refuses GitHub's `/archive/` URLs (403), which is where vcpkg gets most sources. Registries (git) and release assets work. Automap has no setting for this. I got through with vcpkg's own asset-source hook, `X_VCPKG_ASSET_SOURCES=x-script,...`, and a 20-line script that rebuilds each archive with `git fetch` and `git archive | gzip -n`, which reproduces GitHub's bytes, so vcpkg's SHA-512 check still passes. The Automap handoff notes say "builds of public-map libraries run for real only in CI" in such sandboxes; with this script they run locally. It would be worth shipping as a documented recipe, since agent sandboxes commonly have this restriction.
14. **GAP: `sdl3`'s variant description and what vcpkg builds disagree.** The map says the default variant has "IBus input methods … off" (`vcpkg_default_features: false`). The install plan on Linux was `sdl3[core,dbus,ibus,vulkan,wayland,x11]`, which pulls in dbus, libsystemd, libmount, libcap, libxcrypt, lz4, zstd, liblzma, expat and gperf. Dear ImGui's port depends on `sdl3` with its default features, which switches them back on. That roughly doubles the cold build of the day-one composition on Linux, and the map's fact about the variant isn't true of the composition.
15. **GAP: the router skill doesn't say how a testbed becomes a game.** `start` writes a `testbed` target with a `main.cpp` that owns the frame loop, and the manifest records `executable: {target: "testbed", sources: ["main.cpp"]}`. Nothing in the skill, the README or `AGENTS.md` says what the developer may change: whether the target can be renamed, whether sources can move, or that the executable must keep honouring `--frames <n>` and `--probe <file>` for `verify` to work. I learned the protocol by reading the generated `main.cpp` and SPEC §5.6.

## 4. First verification, and `automap extend`

16. **OK: the day-one composition reached `probed` locally.** With the system packages in and downloads working, `automap verify` built SDL3 and Dear ImGui (docking) through vcpkg, ran the 120-frame smoke test headless on llvmpipe, ran the probe build, and wrote `evidence/linux-x64-clang.json`: about 5½ minutes cold on 4 cores. A second composition with the same libraries verified in 9 seconds from vcpkg's binary cache.
17. **OK: `extend` is quick and does what the spec says.** I added spdlog, GLM, stb_image, miniaudio, Tracy and SDL_shadercross one at a time. Each wrote 6 to 16 files, put the library in its slots, and moved the manifest's choices by itself (`diagnostics.log` to `logging-slot`, `diagnostics.profiler` to `profiling-slot`). The `AGENTS.md` slots line kept up.
18. **ENV: a second kind of download was blocked, and I stopped there.** spdlog's `fmt` port fetches a patch from a GitHub commit URL, which the proxy also refuses. Extending my download script to cover it, and building a library from a git clone outside vcpkg, were both declined by this sandbox's own policy checks, so I didn't. From here on, the full composition was verified only in CI. Locally I kept a preview build of the game that links the vcpkg packages already built and stubs the spdlog and Tracy glue; it is not the Automap build and produces no evidence.
19. **FRICTION: six `extend`s in a row failed the same way, and nothing said so.** Every step after spdlog reported `BUILD_FAILED` with the same details file, which each run overwrote. The cause was one download of one port, the same every time. The result could carry the first error line of the log (here: `error: building fmt:x64-linux failed with: BUILD_FAILED`, and the URL that failed), or classify a failed download as `FETCH_FAILED` as `automap fetch` does, so an agent doesn't open a 170-line log to learn it's the network.
20. **OK: `extend` writes the composition even when the build fails,** so the repo was complete and consistent for CI to pick up.

## 5. CI

21. **GAP: the reference workflow doesn't fit a game.** The router skill offers `zach/automap/.github/workflows/automap-verify.yml`. I read it and wrote my own instead, because:
    - it always runs Windows, Linux and macOS, whatever the manifest's `platforms` say (mine: Windows and Linux);
    - it installs the CLI with `go install ...@main`, not the release the composition was written with;
    - it runs only on pushes to `main` in the skill's caller, and commits evidence back to the branch, which doesn't suit a feature branch;
    - it doesn't upload `build/automap/*.log`, so when a build fails on a runner the `details_file` the result names can't be read;
    - it keeps nothing but evidence: a game also needs the built executable.
    My workflow downloads the release binary, checks its SHA-256, runs `automap verify --json`, prints the tail of each log on failure and uploads logs and evidence as an artifact.
22. **OK: the eight-library composition reached `probed` on Windows and on Linux at the first CI run,** with no change to any glue: SDL3, Dear ImGui, spdlog, GLM, stb_image, miniaudio, Tracy and SDL_shadercross. On Windows this was about five minutes from a cold runner. This is the strongest thing I can say for Automap: I never opened a vcpkg port, a CMake find-module or a library's build docs to get eight libraries building and wired on two platforms.
23. **OK: the released Windows binary just works on a runner:** one file, no install.

## 6. The private map: text and data files

The design names two gaps in the public map: text and fonts, and data files. I filled them from a private map in `automap-private/`, with stb_truetype and nlohmann/json.

24. **OK: a private map is easy to start.** `map.json` with an id, a `private_maps` entry in the manifest, and `automap show` and `automap find --slot` answer from it at once. Private slots work: I added `text` and `data-files`, which the public map doesn't have.
25. **FRICTION: there's no guide to writing one.** I worked from SPEC §7, the example in `docs/spec/examples/private-map/` and by copying the public map's `stb-image` files. A developer with only the CLI and the router skill has neither: the skill never mentions private maps. `automap show recipe` of a similar public recipe is the best starting point, and nothing says so.
26. **OK: validation errors are specific.** Each mistake came back as one failure with a code and a sentence I could act on:
    - `MANIFEST_INVALID`: "private map spintacular at automap-private has no commit: the lock pins each private map at the last commit that changed it, so commit it to git";
    - `NO_BUILD_FRAGMENT(nlohmann-json)`: "The map has no library recipe with a build fragment";
    - `MAP_INVALID(automap-private/libraries/stb-truetype.json)`: "versions/0: missing property 'build_backend'".
27. **FRICTION: every change to a private map needs a git commit before the CLI will read it for a composition.** Getting two libraries in took five commits of work in progress. Reading the working tree, with a warning that the lock can't pin it yet, would make the loop much shorter.
28. **GAP (bug): two map libraries that share a vcpkg port break `vcpkg.json`.** stb_truetype ships in the same `stb` port as the public map's stb_image. With both in the composition the CLI wrote `stb` twice into `dependencies` and twice into `overrides`, and vcpkg refused the manifest: `$.overrides[8] (an override): stb already has an override`. `vcpkg.json` is the CLI's file, so I couldn't fix it by hand. The workaround was to recast stb_truetype as an in-repo library (`source.kind: path`, `third_party/stb-truetype/CMakeLists.txt`) that defines a target over the header the stb port already installs. It works, but the map now says something untrue about where the library comes from. The CLI should merge ports by name (and the union of their features).
29. **GAP: nothing re-resolves a library whose map entry changed, and nothing removes one.** After I edited the private library, `verify` refused with `LOCK_MISMATCH(stb-truetype)` (printed twice). There is no `automap resolve` and no `automap remove`. `automap upgrade stb-truetype` turned out to do it, but:
    - `upgrade` is missing from the usage text (note 3);
    - its first answer was "The composition doesn't match its own map release … NO_BUILD_FRAGMENT", which read as a problem with the public map release, not with my private map;
    - it reported "0 files updated" although the private recipe's build fragment had changed and my copy still matched the old reference. It seems to compare only across public map releases, so reference glue that changes in a private map never reaches the repo. I copied the fragment by hand.
30. **OK: the allocation binding and probe I wrote for stb_truetype pass on both platforms.** The contract is clear enough to write against: route `STBTT_malloc` and `STBTT_free` to `am::alloc`, check `routed_count` moves in a probe, describe a seeded violation as a patch. That is about 40 lines for a library the map doesn't know.

## 7. Turning the testbed into a game

31. **OK: the facades are the right seam for game code.** The game logs through `am::diag::log`, profiles with `am::diag::Zone` and reads files through `am::assets::read`. It never includes spdlog or Tracy. That also made the local preview build possible: two stub functions stood in for both libraries.
32. **OK: the manifest's `executable` can be edited by hand.** I renamed the target to `spintacular`, pointed `sources` at `game/app/main.cpp`, replaced the generated `CMakeLists.txt` with the game's own (still including `cmake/automap/automap.cmake` once), and `verify` built and ran the game as its smoke test. Two things I had to find in the CLI's source: the executable must land in the build directory's root, and it is run from there, so the game copies its assets beside itself after building.
33. **FRICTION: the Dear ImGui pairing's reference glue owns the frame.** `am_pair_imgui_sdl3_begin_frame` polls every SDL event itself and `am_pair_imgui_sdl3_end_frame` acquires the swapchain, clears it and submits. A game needs the events and has its own render passes, so I wrote the frame loop again in `game/app/app.cpp` from the same calls. Reference glue that offered `process_event`, `new_frame` and `render(commands, pass)` separately would be usable as it is.
34. **FRICTION: SDL3's setup glue hard-codes the window** ("Automap testbed", 1280 by 720). I edited the glue, which is allowed, but a title and size are the first things any game changes, and the edit means a future `upgrade` will report this file as diverged.
35. **GAP: SDL_shadercross is in the map, but there's no path from shader source to the SPIR-V its glue takes.** `am_shadercross_create_shader` wants SPIR-V bytes. Nothing in the map, the testbed or the recipe notes says how to make them. vcpkg had already installed `dxc` under `vcpkg_installed/<triplet>/tools/directx-dxc/` as a dependency, so I wrote `tools/compile_shaders.py` to compile the game's two HLSL shaders with it and commit the result as a header. A recipe note naming the tool, or a CMake function in the build fragment, would close this.
36. **OK: miniaudio's glue fits a game as written.** The context carries one `ma_engine`; the game builds sounds on it. `AUTOMAP_MINIAUDIO_BACKEND=null` gave silent, device-free runs in CI without a line of game code.
37. **GAP: `start` doesn't ignore its own build directory.** `verify` builds into `build/automap/`, and nothing adds `build/` to `.gitignore`.
38. **GAP: Automap stops at a Debug build.** `verify` configures `-DCMAKE_BUILD_TYPE=Debug` and builds one target. A release build, a second executable (the balance simulation), tests and packaging were all mine to arrange. That is a fair boundary, but `AGENTS.md`'s build line is the only hint of how, and it assumes `VCPKG_ROOT`, which the CLI's own bootstrap doesn't set.
39. **GAP (bug): an in-repo library's pin breaks on a Windows checkout.** The first CI run with the private map failed on Windows before building anything: `LOCK_MISMATCH(stb-truetype)`: "stb-truetype's source in third_party/stb-truetype has changed since the lock pinned it". Nothing had changed. The lock pins a `path` library by the bytes of its files, the lock was written on Linux, and git on the Windows runner checks text files out with CRLF line endings. Linux passed. The fix on my side was a `.gitattributes` forcing LF; the CLI should hash content with line endings normalized, or hash what git has committed. The message itself was good: it named the directory and the command to re-resolve.

## 8. Verifying and shipping the game

40. **OK: the game itself verifies as the composition's executable.** With the manifest pointing at the game, `automap verify` on both CI platforms built it (MSVC and clang), ran it headless for 120 frames as the smoke test, ran every probe inside it, including the private map's, and reached `probed`. The game honours `--frames` and `--probe` in its own `main`, copied from the testbed's.
41. **OK: the Windows build is what the composition promises.** The same code and glue render through Direct3D 12 on Windows and Vulkan on Linux; screenshots from the two CI runners match. The game's shaders are SPIR-V, turned into DXBC at startup by the pairing glue.
42. **GAP: a fact about SDL_shadercross doesn't hold for the build the map produces.** The recipe's notes say Direct3D 12 "gets DXBC, compiled through the system's d3dcompiler_47.dll, so a game needs no DXC at runtime". The `SDL3_shadercross.dll` that the Automap registry's port builds imports `dxcompiler.dll`, so the game won't start without that 18 MB DLL beside it. It's most of the download.
43. **GAP: the map's one Tracy variant can't ship, and choices can't differ by build type.** The variant "records from startup and holds what it records until a profiler connects", and listens on the network. In a player's copy that is memory that only grows, and a listening socket, which on Windows can raise a firewall prompt at first launch (I didn't test for the prompt). I wanted Tracy in development builds and not in the release, but a composition has one set of slots and choices for every build type. An on-demand, localhost-only variant would be shippable; today's diagnostics probe for Tracy would fail it, because it expects zones to queue with no profiler connected.
44. **GAP: there is no `automap remove`.** I took Tracy out by deleting it from the manifest's `slots`, `variants` and `glue` by hand, setting `diagnostics.profiler` to `none`, and running `automap upgrade`, which rewrote the lock, `vcpkg.json`, `automap.cmake` and the choices header. `verify` had pointed the way: "the lock pins [… tracy] but the manifest's slots hold […]; re-resolve with automap extend or upgrade". The library's build fragment and glue directory stayed behind as orphans; I deleted them.
45. **OK: the facade made that removal free for the game.** Game code opens `am::diag::Zone`s; with the slot empty they go nowhere and cost next to nothing. `automap extend tracy` puts profiling back for a session.
46. **FRICTION: `automap find <query>` doesn't search the way a need is phrased.** `find audio`, `find json` and `find physics` each found the library; `find text` and `find font` found nothing, though `find --slot text` lists stb_truetype. Searching slot ids and descriptions for every map layer, and saying which slots exist when nothing matches, would help the "is there a library for X?" question the tool is for.
47. **OK: `verify --platform` on the wrong machine says what to do:** "Run verify on a windows-x64-msvc machine to verify that platform."

## 9. Two more features, tried in CI for the record

48. **OK: `automap verify --seed` proved the private map's probe.** `automap verify --seed allocation.routed-through-facade:stb-truetype` applied my seeded violation (stb_truetype compiled without its allocation macros) in a scratch copy and reported: "The probe caught the seeded violation … ALLOC_NOT_ROUTED(stb-truetype)". That is a real check on glue and a probe I wrote myself, for one command. One oddity: the result carries `"level": "smoke"`, which reads as if the composition had dropped a level.
49. **OK: `automap eject` leaves a game that builds and runs without Automap.** On a copy of the repo, `eject` copied three Automap registry ports into `ports/`, rewrote `vcpkg-configuration.json` and removed the manifest and lock. A plain `cmake` configure and build of the game then worked, and the game ran its 120 frames. Two leftovers: the `AGENTS.md` section and the router skill still tell an agent to go through the `automap` CLI and a manifest that no longer exist, and `automap-private/` and `evidence/` stay behind.
50. **OK: the evidence in `evidence/` is CI's.** Both files were written by `automap verify` on the runners and copied in from the run's artifact: `probed` on `windows-x64-msvc` and on `linux-x64-clang`, 29 rules each, every one `pass` or `not-applicable`. Each names this repo's workflow as its `developer-ci` verifier. They are marked unsigned: signing is done by the reference workflow's attestation step, and nothing but that workflow's source says what a workflow of one's own must do to get signed evidence.
